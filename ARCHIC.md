# Archic Project Standard — Business-first UI

This repository must follow the Archic design rule: **the interface exists to expose the business, not to decorate text**.

## 1. Start from the customer's decision

Before adding a section or component, write down:

- What is the visitor trying to see, compare, choose, book, buy or understand here?
- What real business content answers that question?
- What action should be possible from this component?
- Why does this component exist in this business specifically?

If the answer is only "to explain the service", do not build the section yet. Look for a product, price, availability, location, configuration, comparison, proof, media or workflow that can communicate the same thing more directly.

## 2. No reusable agency-template language

Do not default to the same component patterns across Archic projects.

Avoid as a default:
- three equal feature cards;
- icon + heading + short paragraph grids;
- repeated dark/light sections with identical layouts;
- generic floating cards over heroes;
- generic "how it works" step sections;
- random statistics used as decoration;
- decorative gradients or blobs unrelated to the brand;
- long pages built mainly from headings and explanatory copy.

A component may look similar to another project only when the business problem genuinely requires the same interaction.

## 3. Components are domain components

Name and design components around the business.

For PRISMA, examples are:
- `HeroVehicleStage`
- `QuickMatchLab`
- `RequestConfigurator`
- `VehicleActions`
- `CompareTray`
- `ComparisonExperience`

Prefer these over generic names such as `FeatureSection`, `InfoCards` or `CTASection`.

## 4. Real content has priority

Use, in order of preference:
1. real client/business assets and data;
2. verified public business data;
3. carefully curated editorial assets;
4. placeholders only when explicitly labelled as placeholders.

Never present an unrelated image as if it were the exact product. Never present demo KPIs as real company performance.

## 5. Product-first first viewport

The first viewport should expose the thing the customer came for.

Examples:
- automotive: vehicle, model, price/reference, configuration or search;
- restaurant: food, atmosphere, menu/reservation availability;
- real estate: property, location, price, key details;
- services: the actual work, result, availability or booking path.

Brand narrative supports the product. It does not replace it.

## 6. Text is support, not inventory

Headlines must carry meaning, not merely fill a layout.

If a section is mostly:
- eyebrow;
- large heading;
- paragraph;
- empty visual space;

challenge the section. Replace explanation with real content or an interaction whenever possible.

## 7. Visual direction is project-specific

Before implementation, define:
- visual references;
- typography rationale;
- image treatment;
- density;
- motion language;
- grid logic;
- interaction model;
- what the site must deliberately NOT look like.

Do not transfer a palette, card radius, section rhythm or grid from another Archic project by habit.

## 8. Function is part of design

Visible controls must work.

For prototypes:
- filters filter;
- sorting sorts;
- favorites persist;
- compare compares;
- configurators produce a meaningful request;
- WhatsApp carries context;
- forms either submit somewhere real or are clearly marked as demo.

Avoid controls that exist only to look functional.

## 9. Architecture must preserve the business asset

A redesign must not destroy:
- SEO routes;
- structured data;
- redirects;
- catalogue data;
- customer workflows;
- analytics;
- accessibility;
- performance.

For migrations, treat the current site as an asset to migrate, not a canvas to replace blindly.

## 10. Definition of done

A project is not "premium" because it is dark, minimal or animated.

It is ready for Archic review when:
- the first viewport immediately exposes the core business;
- the visual language could not be swapped onto an unrelated business without feeling wrong;
- important actions are functional;
- imagery is intentional;
- demo data is labelled;
- mobile is deliberately designed;
- keyboard/focus/reduced-motion states are respected;
- lint, build and dependency audit pass;
- the deployed version receives visual and functional QA.

If a page could be generated by changing the logo and colors of another Archic project, the design is not finished.
